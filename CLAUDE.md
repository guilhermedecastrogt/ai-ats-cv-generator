# CLAUDE.md — AI CV Generator

This file contains instructions for the AI agent (Claude Code or similar) working in this repository.

## Purpose

This repository generates targeted, ATS-friendly, one-page LaTeX CVs from the candidate's professional profile.
The AI reads the context files, tailors each CV variant to the target role, and outputs compiled PDFs.

---

## How to Use This Repo (for the candidate)

1. Fill in `context/aboutme.md` with your real professional information.
2. Optionally fill in `context/linkedin.md` and `context/github.md` for extra detail.
3. Fill in `context/target-roles.md` with the roles and variants you want.
4. Open this repo in Claude Code (or any Claude-powered editor).
5. Tell the AI: **"Generate my CVs"** — it will read your context and create all variants.
6. Run `python3 compile.py` to build all PDFs.

---

## AI Agent Instructions

### Before generating any CV

**Read every file inside `context/` before doing anything else.**

The user may have placed any number of files there — `.text`, `.md`, `.txt`, or any other format. Read them all, regardless of filename or extension. Do not assume which files exist; list the folder and read every file you find.

Common files users place in `context/`:
- Their professional profile or current CV
- LinkedIn export (PDF text or manual copy-paste)
- GitHub project report (AI-generated or manual)
- A job description they are applying to right now
- Notes about roles they want, technologies to emphasize, or things to avoid
- Any other professional context they find relevant

**Treat all files in `context/` as a single unified source of truth.** If two files contain conflicting information, flag the conflict to the user before proceeding.

**Never fabricate** experience, dates, metrics, companies, certifications, or education. Only use what is present in the context files.

---

### Generating CV Variants

For each variant listed in `context/target-roles.md`:

1. Create a folder under `output/` (e.g., `output/backend/`).
2. Create a filled `cv_<variant>.tex` file using the LaTeX template from `template/cv_template.tex`.
3. Create a `summary.md` in the same folder (see requirements below).

The CV must fit on **one page**. If it is too long, shorten bullet points first — do not remove entire jobs.

## CV Bullet Point Strategy — Highest Priority

The main quality factor of every CV generated by this repository is the quality of its bullet points.
The AI must treat bullet points as the core product of the CV.

Every bullet point must be written to maximize:
- ATS keyword matching
- recruiter readability
- measurable impact
- seniority perception
- relevance to the target role
- clarity within one page

**A CV bullet is only valid if it answers at least two of these questions:**
- What did the candidate build, improve, automate, design, or lead?
- Which technology, architecture, or process was used?
- What business, product, or engineering problem did it solve?
- What measurable or observable result did it create?
- Why is this relevant to the target role?

If a bullet answers only one question, rewrite it.

---

## Bullet Point Frameworks

Every experience bullet must follow one of these structures whenever possible.

### XYZ Method (default)

Use the XYZ method as the default bullet point format:

```
Accomplished [X], measured by [Y], by doing [Z].
```

Where:
- **X** = what was achieved
- **Y** = measurable result, scale, business impact, performance gain, revenue, users, systems, volume, speed, reliability, cost, or productivity
- **Z** = technical action, stack, architecture, process, or responsibility

Examples:
```
Improved workshop productivity tracking by 80% by building a .NET-based workforce management system integrated with operational repair workflows.
Reduced deployment friction by containerizing backend services with Docker and automating release pipelines through GitHub Actions.
Increased system maintainability by designing RESTful APIs with Clean Architecture, Entity Framework Core, and structured service boundaries.
```

### S.T.A.R Method (reasoning model)

Use S.T.A.R as the internal reasoning model behind each bullet. Do **not** label bullets with Situation/Task/Action/Result — compress the reasoning into one concise professional sentence.

- **Situation** = context or problem
- **Task** = responsibility or objective
- **Action** = what the candidate did
- **Result** = measurable or observable outcome

Example reasoning:
```
Situation: The company needed better visibility over technician productivity.
Task: Build an internal system to track repair time and productivity.
Action: Developed a workforce management platform using .NET, SQL, and operational dashboards.
Result: Improved productivity tracking and enabled data-driven reporting.

Final CV bullet:
Built a .NET workforce management platform to track technician productivity, enabling data-driven repair reporting and improving operational visibility.
```

---

## Bullet Point Requirements

Each bullet point must:
- Start with a strong action verb
- Include a specific technical action
- Include a business, product, engineering, or operational outcome
- Mention relevant technologies naturally
- Be tailored to the target role
- Be concise enough for a one-page CV
- Avoid sounding like a generic job description
- Prefer quantified impact when supported by context
- Use implied impact when exact metrics are unavailable

**Priority order when writing bullets:**
1. Measurable business impact
2. System scale or technical complexity
3. Ownership and responsibility
4. Architecture and engineering decisions
5. Technologies used
6. Collaboration or leadership
7. Routine implementation details

A bullet with impact is better than a bullet that only lists tools.

---

## Bullet Point Formula Library

Use these formulas when transforming raw experience into CV bullets.

**Formula 1 — Impact + Technical Action**
```
Improved [result] by [action] using [technology].
```
> Improved internal reporting accuracy by building automated dashboards connected to operational repair data.

**Formula 2 — Built + System + Outcome**
```
Built [system/product] with [stack], enabling [business outcome].
```
> Built a workforce management platform with .NET and SQL databases, enabling managers to monitor technician productivity and repair performance.

**Formula 3 — Designed + Architecture + Maintainability**
```
Designed [architecture/API/data model] using [principle/tool], improving [maintainability/scalability/reliability].
```
> Designed backend service boundaries using Clean Architecture and DDD principles, improving maintainability across business-critical applications.

**Formula 4 — Automated + Process + Efficiency**
```
Automated [manual process] using [tool/stack], reducing [manual effort/risk/time].
```
> Automated deployment workflows with Docker and GitHub Actions, reducing manual release effort and improving environment consistency.

**Formula 5 — Integrated + Systems + Business Flow**
```
Integrated [system A] with [system B], enabling [workflow/result].
```
> Integrated internal systems with ERP data flows, enabling more reliable operational reporting and reducing fragmented manual processes.

**Formula 6 — Led + Delivery + Cross-functional Impact**
```
Led [project/delivery/process] across [teams/scope], ensuring [result].
```
> Led technical delivery across software, product, and business stakeholders, ensuring aligned execution from requirements to deployment.

## Metrics and Impact Rules

Use exact metrics **only** when they are present in the context files. Never invent numbers.

Allowed metric types: revenue generated, percentage improvement, number of users, number of services, number of integrations, request volume, deployment frequency, performance improvement, cost reduction, productivity gain, team size, project duration, number of clients, number of systems delivered.

When no metric is available, use non-fabricated impact language:
- improved operational visibility
- reduced manual work
- increased maintainability
- supported faster delivery
- strengthened deployment reliability
- enabled data-driven decisions
- simplified cross-system integration
- improved user experience
- supported scalable workflows
- reduced repetitive tasks

---

## Bullet Point Quality Levels

Internally classify every bullet before finalizing. Target Level 3 or 4 for all bullets.

| Level | Description | Example |
|-------|-------------|---------|
| 1 — Weak | Generic, task-based, no impact | `Developed backend features using .NET and SQL Server.` |
| 2 — Acceptable | Specific action and stack, but weak result | `Developed backend APIs using .NET and SQL Server for internal business systems.` |
| 3 — Strong | Action, technology, and outcome | `Developed .NET APIs with SQL Server to automate internal business workflows and improve operational data access.` |
| 4 — Excellent | Action, metric, technology, ownership, and outcome | `Improved workshop productivity tracking by 80% by building a .NET workforce management platform integrated with repair operations and reporting workflows.` |

Do not use Level 1 bullets. Use Level 2 only when space is critically limited.

---

## No Responsibility-Only Bullets

Never write a bullet that only describes a responsibility.

**Bad:**
```
Responsible for maintaining APIs and databases.
```

**Better:**
```
Maintained .NET APIs and relational databases supporting internal business workflows, improving reliability and long-term maintainability.
```

**Best:**
```
Improved reliability of internal business workflows by maintaining .NET APIs, optimizing relational database access, and standardizing backend service patterns.
```

---

## Strong Action Verbs

Use varied verbs. Preferred: Built, Designed, Developed, Delivered, Implemented, Architected, Integrated, Automated, Optimized, Refactored, Containerized, Deployed, Led, Coordinated, Improved, Reduced, Increased, Enabled, Standardized, Migrated, Maintained, Scaled, Secured, Streamlined.

Avoid weak verbs: Helped, Worked on, Assisted with, Participated in, Was responsible for, Used, Made, Did, Created stuff for.

## Bullet Point Tailoring by Variant

### `backend/`
Prioritize: APIs, databases, integrations, system design, performance, reliability, authentication, architecture, backend ownership, service boundaries, data modeling.

Preferred structure: `Designed [backend/system/API] using [technology], enabling [business/technical outcome].`

> Designed RESTful APIs with .NET, Entity Framework Core, and SQL Server, supporting scalable business workflows and maintainable backend services.

### `fullstack/`
Prioritize: end-to-end features, frontend + backend integration, product delivery, React/Next.js, API design, database-backed applications, user experience, ownership from UI to deployment.

Preferred structure: `Delivered [feature/product] across [frontend] and [backend], improving [user/business outcome].`

> Delivered full-stack features with React, Next.js, .NET APIs, and SQL databases, improving product usability across internal business workflows.

### `devops/`
Prioritize: Docker, CI/CD, Linux deployments, Nginx, observability, automation, infrastructure reliability, container orchestration, deployment pipelines.

Preferred structure: `Automated [deployment/infrastructure process] using [tools], reducing [manual effort/risk/friction].`

> Containerized backend services with Docker and automated deployments through GitHub Actions, improving release consistency and reducing manual deployment effort.

### `frontend/`
Prioritize: React, Next.js, TypeScript, UI performance, responsive interfaces, SEO, UX, conversion, design implementation, frontend architecture.

Preferred structure: `Built [interface/page/application] with [frontend stack], improving [UX/performance/conversion].`

> Built responsive interfaces with React, Next.js, and TypeScript, improving usability and supporting SEO-driven product experiences.

### `python/`
Prioritize: scripting, automation, data processing, AI integrations, APIs, workflow automation, backend utilities, analysis pipelines.

Preferred structure: `Automated [process] with Python, reducing [manual effort] and enabling [outcome].`

> Automated data extraction and processing workflows with Python, reducing manual analysis effort and supporting faster business decisions.

### `general/`
Show breadth across all areas. Emphasize adaptability, ownership, and full-stack capability. Do not suppress any domain.

## Bullet Point Density Rules

- Each recent or highly relevant job: 3–5 bullets
- Older or less relevant jobs: 1–3 bullets
- Projects: 1–3 bullets each
- Do not write paragraphs inside experience sections
- Do not exceed two lines per bullet
- Prefer fewer strong bullets over many weak ones

**When the CV is too long:**
1. Shorten bullets first
2. Remove the weakest bullet from the least relevant job
3. Only remove a full experience if it is irrelevant to the target role and already represented elsewhere

---

## Bullet Point Anti-Patterns

Do not generate:
```
Responsible for developing applications.
Worked with frontend and backend.
Used Docker and GitHub Actions.
Helped the team build systems.
Participated in meetings and agile ceremonies.
```

Rewrite as:
```
Delivered backend and frontend features across business-critical applications, connecting React interfaces with .NET APIs and relational databases.
Automated deployment workflows with Docker and GitHub Actions, improving release consistency across Linux-based environments.
```

## Bullet Point Revision Process

Before saving any `.tex` file, revise every bullet against this checklist:

- [ ] Starts with a strong verb
- [ ] Shows what the candidate actually did
- [ ] Includes the relevant technical stack
- [ ] Shows why the work mattered
- [ ] Uses a metric if one is available in the context
- [ ] Is tailored to the target role
- [ ] Is one line or two lines max
- [ ] Is stronger than a generic job description
- [ ] Does not repeat the same verb in consecutive bullets
- [ ] Does not contain inflated or fabricated claims

If a bullet fails two or more checks, rewrite it.

---

## Job Description Tailoring for Bullets

When a job description is provided, extract: required technologies, preferred technologies, responsibilities, domain keywords, seniority signals, soft skills, repeated terms, and business context.

Then rewrite bullets to naturally include the strongest matching keywords.

**Do not keyword-stuff.**

Bad:
```
Built APIs using .NET, REST, SQL, Docker, Agile, Scrum, CI/CD, cloud, microservices, backend, frontend.
```

Good:
```
Built RESTful APIs with .NET and SQL Server, applying clean service boundaries and Docker-based deployment workflows in agile delivery environments.
```

---

## Final Bullet Review

Before saving the `.tex` file, run this final pass:

1. Remove duplicate verbs across bullets in the same role
2. Remove repeated technologies when unnecessary
3. Move the strongest bullet to the top of each experience block
4. Ensure the first bullet of each role is impact-driven
5. Ensure the most relevant keywords appear in the top half of the CV
6. Ensure every bullet supports the target role
7. Ensure the CV does not sound inflated or fabricated
8. Ensure all bullets fit within the one-page constraint

---

## summary.md Requirements

Every `summary.md` must include these sections:

1. **Target Role** — what role this CV is optimized for
2. **Main ATS Keywords Used** — top 8–12 keywords placed in bullets
3. **Experiences Prioritized** — which jobs were given more space and why
4. **Projects Selected** — which projects were chosen and why
5. **Bullet Point Strategy** — how XYZ and S.T.A.R were applied, which metrics were used, which bullets were adapted for ATS keywords, which bullets were compressed to fit one page
6. **Metrics Used** — list of quantified metrics taken from context
7. **Trade-offs Made to Fit One Page** — what was shortened or removed
8. **Weak Areas or Missing Context** — anything that would make this CV stronger if the candidate had it
9. **Suggestions to Improve Future Versions** — what the candidate should add to their context files

Example `Bullet Point Strategy` section:

```md
## Bullet Point Strategy

The strongest bullets were written using the XYZ method, particularly for the workforce management
system (80% productivity improvement) and Docker deployment workflows (release consistency gain).

S.T.A.R reasoning was used to convert raw responsibilities into outcome-driven bullets. The workforce
management system was framed around the operational problem of tracking technician productivity,
the candidate's responsibility to build the system end-to-end, the .NET + SQL implementation, and
the resulting improvement in operational visibility.

Exact metrics were used only where available in the context files. No unsupported numbers were added.
The bullet for the e-commerce platform used implied impact language ("improved reliability") because
no quantified metric was available.

Three bullets were compressed from two-line to one-line form to stay within the one-page constraint.
```

## LaTeX Rules

- Template uses: `titlesec`, `enumitem`, `hyperref`, `fancyhdr`, `geometry`, `xcolor`, `tabularx`
- Do **not** use `\usepackage[empty]{fullpage}` — `geometry` handles margins
- Escape special characters in body text: `\&`, `\#`, `\$`, `\%`, `\_`
- Use `\href{url}{\underline{display text}}` for links
- Use `--` (en-dash) for date ranges: `Jan 2023 -- Present`
- Always compile twice to resolve cross-references (the compile script does this automatically)
- Target: **one page per CV**

---

## Education Formatting Rule

Show only the degree name and the **start date** — no end date, no "(in progress)" qualifier.

**Why:** ATS systems and AI screeners often auto-disqualify candidates when they detect "(in progress)"
or a future graduation date. Omitting the end date leaves it ambiguous — the system cannot determine
completion status and typically passes the candidate through rather than filtering them out.

**Format:**
```latex
\resumeSubheading
  {Bachelor's Degree, Computer Science}{Jan. 2022}
  {University Name}{City, Country}
```

Do **not** write: `(in progress)`, `(expected 2026)`, `-- Dec. 2026`, or any qualifier signaling incompletion.

## Generating a CV for a Specific Job Posting

If the user pastes a job description, follow this process:

1. Read the job description carefully.
2. Read all context files.
3. Identify the top 5–8 skills/keywords the job requires.
4. Generate a tailored CV that:
   - Opens with a summary sentence referencing the role
   - Leads with the most relevant experiences and projects
   - Uses the job's keywords naturally in bullet points (ATS optimization)
   - Fits on one page
5. Save to `output/tailored/<company-name>/cv_<company-name>.tex`
6. Write a `summary.md` explaining every tailoring decision made

---

## Compiling

After generating `.tex` files, the user runs:
```bash
python3 compile.py
```

This compiles every `.tex` under `output/` into a PDF and cleans auxiliary files.

If LaTeX packages are missing:
```bash
# macOS (MacTeX)
sudo tlmgr update --self
sudo tlmgr install titlesec enumitem collection-latexrecommended

# Ubuntu
sudo apt-get install texlive-full
```

## What NOT to Do

- Do not invent experience, companies, dates, or metrics
- Do not add `(in progress)` to education
- Do not exceed one page
- Do not use `\usepackage[empty]{fullpage}`
- Do not skip reading context files before generating
- Do not generate a CV without also generating its `summary.md`
- Do not write responsibility-only bullets
- Do not write Level 1 or Level 2 bullets unless space is critically limited
- Do not keyword-stuff bullet points
- Do not skip the Final Bullet Review before saving the `.tex` file
